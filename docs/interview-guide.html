Flight Booking Agent: Interview Guide

Your project, from the big picture down to each module. Everything here is checked against the code in flight_booking/app. In interviews, call it "my agentic flight booking assistant".

1. The 60-second pitch

I built a flight booking assistant as a LangGraph agent. The user chats in plain language; the LLM decides which tool to call: search flights, load saved passengers, hold a seat, or create a payment. Flight search goes through an MCP tool server in front of the Duffel airline API, and payments go through Cashfree.

The core design rule is that the model proposes and the application decides. Booking is irreversible, so the graph pauses with a LangGraph interrupt and a human must approve. Approvals are idempotent and expire with the fare. The payment status is a state machine where paid is final, and webhooks are HMAC-verified and deduplicated.

It's served by FastAPI. Sending a message returns 202 immediately, the agent runs in the background, and progress streams to the browser over Server-Sent Events. State lives in PostgreSQL, including the LangGraph checkpointer, so a paused approval survives a restart. It has 62 integration tests against a real server and a real database.
Five words to remember: tools · interrupt · state machine · SSE · checkpointer. If you can explain each one in your own project, you can answer most questions.

2. High-level architecture

Four layers. Each one has a single job, and calls only go downward.

Graph ≈ Coordinator, handler ≈ ViewModel mapping, service ≈ domain/use-case layer, repository ≈ Core Data store wrapper, provider ≈ a protocol-backed network client you mock in XCTest.

3. Life of one message

What happens when the user types "Book me DEL to DXB on Nov 20":

Agent turns take 5–20 seconds, so I don't hold the HTTP request open. The POST returns 202 Accepted, the turn runs as a background task, and the browser follows along on one long-lived SSE stream. Only one turn runs per conversation: a second POST while busy gets a 409 with retryable: true.

4. The LangGraph graph

The router after llm is route_after_llm in graph.py. The order of its checks matters:

if PASSENGER_TOOL in names:  return "passengers"   # nothing to approve without passengers
if "book_flight" in names:   return "approval"     # book never runs before a human says yes
if tool_calls:               return "tools"
return END
The safety rule is in the graph's structure, not the prompt. There is no edge from llm straight to booking: every book_flight tool call goes through the approval node. Even if the model is jailbroken into calling book_flight, it still has to stop there for a human.
This is a custom loop, not the prebuilt create_react_agent. Be ready to say why: I needed routing on the tool name (approval vs passengers vs plain tools), which the prebuilt agent doesn't give you.

5. agent/state.py: the agent's memory

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]   # reducer: APPEND, don't replace
    user_id: str
    booking: dict | None          # shown to the LLM; booking_id = Duffel's ord_…
    payment: dict | None
    db_booking_id: str | None     # our Postgres UUID, never shown to the LLM
    unavailable_offers: list[str] # fares the airline refused

Concept: reducers

Each node returns a partial update. For messages, the reducer operator.add means "append to the list". Every other key is simply overwritten.

Concept: two booking IDs

booking.booking_id is the provider's id (Duffel ord_…). db_booking_id is our Postgres UUID, used by services and as the Cashfree order id. Keeping our own id out of the LLM's view means the model can't confuse or invent internal ids.

A real bug: passing booking: None in every turn's input overwrote the checkpointed booking. The fix was to send only the new message and user_id. Also, LangGraph silently drops input keys not in the schema, so thread_id has to be read from config["configurable"].

6. agent/llm.py: tool calling

  • TOOLS: JSON Schemas, mostly generated from Pydantic: SearchFlights.model_json_schema(). One source of truth for validation and for the prompt.
  • GUIDE: the system prompt. Key rules: "the application asks for approval, don't ask yourself"; "if retryable is false, don't call that tool again with the same arguments".
  • build_messages: adds a second system message with the application's booking and payment state, so the model is told the facts rather than having to remember them.
  • call_llm: rate limiter → semaphore → client.chat.completions.create(..., tools=...), then logs duration and tokens.
  • safe_call_llm: the graph node. It maps timeouts, 429s, connection errors and empty responses to polite fallback replies, so the turn ends cleanly instead of crashing.

Concept: semaphore vs rate limiter asked often

asyncio.Semaphore(3)RateLimiter(rate=5)
Limitshow many calls are in flight at oncehow many calls start per second
Protects againsttoo many open connectionsbursts that trigger 429s
Howa counter; the 4th caller waits until one finishesa lock plus next_time; each caller is scheduled 0.2s after the previous one and sleeps until its slot
async def acquire(self):
    async with self.lock:                      # only the bookkeeping is locked
        now = time.monotonic()
        scheduled = max(now, self.next_time)
        self.next_time = scheduled + self.interval
        delay = scheduled - now
    if delay > 0:
        await asyncio.sleep(delay)             # sleep OUTSIDE the lock
Semaphore ≈ OperationQueue.maxConcurrentOperationCount = 3. The rate limiter is like a throttle on how often operations may start.
The LLM call itself has no retry here: a 429 becomes a polite reply. Retries with exponential backoff and jitter are in the Grounded Answer Engine's gateway (retry.py). Don't mix the two projects up in an answer.

7. agent/approval.py: human in the loop

Concept: interrupt() and resume

  1. interrupt(payload) stops the graph and saves state to the checkpointer. The runner sees __interrupt__ and publishes approval.required.
  2. The user clicks. The API calls graph.ainvoke(Command(resume="approved"), config).
  3. The node re-runs from the top, and this time interrupt() returns the decision.
Because the node re-runs, anything before interrupt() runs twice. So: (a) the approval_id comes from the tool call id (ap_{tool_call_id}), which is the same on both runs; (b) approval.required is published by the runner, not inside the node, or it would be sent twice.

Concept: the app authorises, not the model

  • Idempotent: a double-click with the same decision gets 202 and nothing runs twice (session.resolved). A different decision gets 409 approval_already_resolved.
  • Expires with the fare: approving after expires_at is turned into "expired" in routes.decide. Nothing is booked.
  • Live price: the approval card re-fetches the offer, so the user never approves a stale price.
  • Dead fares: when the airline refuses an offer (OfferUnavailable), its id goes into unavailable_offers and is never offered for approval again.

Concept: every tool call needs a reply

skip_tool_calls() writes a role: tool message for every pending tool call. The OpenAI API rejects the next request if an assistant tool call has no matching tool message.

8. agent/tools.py + handlers.py: errors as data

HANDLERS = {"search_flights": ..., "get_saved_passengers": ..., "book_flight": ...,
            "create_payment": ..., "complete_payment": ...}

try:
    return await handler(tool_call, state)
except OfferUnavailable as exc:   # mark fare dead, retryable: False
except AppError as exc:           # {"error": "..."}  → back to the LLM
except httpx.HTTPError as exc:    # "Upstream provider error"
Expected failures go back to the LLM as data, not exceptions. If the model sends bad arguments, Pydantic raises a ValidationError, I turn it into InvalidToolArguments, and the model sees the error as a tool message and corrects itself on the next step. That's a self-correction loop without a separate retry layer.
def parse_arguments[T: BaseModel](tool_call, model: type[T]) -> T:
    try:
        return model.model_validate_json(tool_call["function"]["arguments"] or "{}")
    except ValidationError as exc:
        raise InvalidToolArguments(f"Invalid arguments for {tool_name}: {exc}") from exc
  • The airline's response is validated too: Flight.model_validate(...), and a failure becomes InvalidUpstreamResponse. Never trust either side: not the LLM, not the vendor.
  • Tools in one LLM message run in order, and later calls see earlier calls' updates: {**state, **updates}.
  • Each tool is a UI "step" (progress.start_step / finish_step), and each is logged with its duration and ok/error.
parse_arguments[T: BaseModel] is Python 3.12 generic syntax, like func parse<T: Decodable>(_ type: T.Type) with JSONDecoder.

9. mcp/: Model Context Protocol

  • MCP is a standard protocol for exposing tools to AI apps: a server declares tools with typed inputs, and any MCP client can list and call them. Here the transport is stdio: the client starts the server as a subprocess and talks JSON-RPC over stdin/stdout.
  • The server (mcp/server.py) uses the MCP SDK v2 MCPServer class (it was called FastMCP in 1.x) with one tool, search_flights. It validates inputs with the same SearchFlights Pydantic model.
  • The client passes the environment explicitly: only PATH and FLIGHT_VENDOR_TOKEN. A stdio server does not inherit your .env; this was a real bug found in Docker.
I put flight search behind an MCP server so the tool is reusable: Claude Desktop or any other MCP client could call the same search. The agent's other actions, like booking and payment, are direct service calls, because they need the user's database session and the approval gate.
Know the trade-off: the client opens a new subprocess per search (async with Client(...)). That's simple, but it costs process start-up on every call. In production I'd keep one long-lived session, or use the Streamable HTTP transport.

10. services/ + db/: rules and data

BookingService.book_flight, step by step:

  1. Passengers must exist, belong to this user, and be complete (Duffel needs title, gender, date of birth, email, phone).
  2. Re-fetch the offer, so we book the current price.
  3. Place the hold with the provider.
  4. Save the flight and booking, then commit() as one transaction.

Concept: who commits?

Services commit; repositories only flush. This is the unit-of-work pattern: one service method equals one transaction, so a booking is never half-saved.

Tables

Stack: SQLAlchemy 2 async + asyncpg, Alembic migrations. The LangGraph checkpointer uses psycopg (a different driver) on the same database, hence libpq_url().

11. Payments + webhook: safe to retry

ALLOWED = {
    CREATED: {PENDING, PAID, FAILED, EXPIRED},
    PENDING: {PAID, FAILED, EXPIRED},
    FAILED:  {PAID},          # a late success still wins
    EXPIRED: {PAID},
    PAID:    set(),           # terminal
}
# _transition: same status or illegal move → change nothing

The webhook, in order

  1. Read the raw body, then verify the HMAC signature (Cashfree signs timestamp + body with a shared secret). Bad signature → 401.
  2. Parse the JSON and find the order id, which is our booking UUID.
  3. Deduplicate on the unique (provider, event_id). A duplicate is ignored.
  4. Apply it through PaymentService.apply_provider_status, the same path the manual /sync button uses.
  5. Return 200 quickly, even for duplicates, because Cashfree retries anything else.
Webhooks are delivered at-least-once and can arrive out of order. So I made processing idempotent with a unique constraint on the provider's event id, and made order irrelevant with a state machine: once paid, a late "failed" event changes nothing.
Honest status: in the live sandbox, complete_payment ends at pending, because there's no checkout frontend to actually pay. The paid → confirmed path is verified with a mock payment provider in tests.

The runner: everything is a "turn"

turn.started → status busy → (steps, messages, domain events) → turn.completed → idle | awaiting

The turn() context manager guarantees that turn.completed is always sent, even when something fails. Exceptions become an error event, never a hung spinner.

Concept: SSE stream with reconnect

  1. Subscribe first, then take a snapshot. If the order were reversed, an event published between the two steps would be lost.
  2. Send session.snapshot with id = the last event id, so the browser redraws everything from it.
  3. Stream live events, skipping ids ≤ snapshot id, because those are already in the snapshot.
  4. Send a heartbeat : ping every N seconds so proxies don't close an idle connection.

Event ids increase per thread and are never reused. After a restart, restore_counter continues numbering from the saved session.

I chose SSE over WebSockets because the traffic is one-directional, server to browser. User actions are plain POSTs. SSE works over normal HTTP, reconnects automatically, and supports Last-Event-ID.

Concept: ContextVar for progress

progress.py stores the current turn in a ContextVar. Graph nodes call progress.start_step(...) without passing the turn around, and each asyncio task sees its own value, so two conversations never mix events.

ContextVar ≈ Swift's @TaskLocal: a value scoped to the current task and inherited by its child tasks.
Keep a reference to every asyncio.create_task task. The event loop holds only a weak reference, so an unreferenced task can be garbage-collected mid-run.

14. Auth, logging, errors

  • Auth: Firebase ID tokens verified without firebase-admin. The service fetches Google's public certificates, checks the RS256 signature, the audience (our project), the issuer and the expiry, then maps firebase_uid to a user. Someone else's thread → 404, not 403, so we don't reveal that it exists. SSE sends the token as ?access_token=, because the browser's EventSource can't set headers.
  • Logging: JSON lines with request_id, thread_id and turn_id; for each LLM call, the duration plus input and output tokens; for each tool, the duration and ok/error; redact() for secrets.
  • Errors: one AppError hierarchy (OfferUnavailable, UpstreamRateLimited, ...). api/errors.py maps each one to an HTTP code and a stable error code, with retryable where it applies.

15. Tests: 62 integration tests

  • A real uvicorn server and a real Postgres (flight_booking_test). Fakes only at the edges: LLM, Duffel and Cashfree (tests/fakes.py).

17. Real bug stories (use these for "tell me about a hard bug")

1. Tool events never reached the browser

S: Tool steps were missing from the UI. T: Find why the node didn't know its conversation. A: I found that LangGraph silently drops input keys that aren't in the state schema, so _thread_id never arrived. I changed the nodes to read config["configurable"]["thread_id"] through a RunnableConfig parameter. R: Events flowed, and I learned to treat the state schema as a contract.

2. Duplicate approval cards

I published approval.required inside the node. On resume, LangGraph re-runs the node from the top, so the event fired twice. Fix: publish it from the runner when it sees __interrupt__, and derive approval_id from the tool call id so it's the same on both runs.

3. Booking state wiped every turn

Each new message's input contained booking: None, which overwrote the checkpointed booking. Fix: send only messages and user_id. Input is an update, not a full replacement of the state.

4. The airline refused offers that looked valid

In Duffel test mode, real carriers returned 422 offer_no_longer_available on hold, even though GET on the offer was 200. Fix: map it to OfferUnavailable, remember the fare in unavailable_offers, return retryable: false to the model, and have the approval gate refuse that fare from then on. The model then searches again on its own.

5. MCP worked locally, failed in Docker

The stdio MCP server is a subprocess that only gets the environment you pass it. Locally the token happened to be found; in Docker there's no .env. Fix: pass FLIGHT_VENDOR_TOKEN explicitly in StdioServerParameters(env=...).

6. ~15k input tokens per LLM call (performance / cost)

Token logging showed each call sending ~15k tokens, because the 50 flight offers from the search stayed in the message history. It's a measured finding you can discuss: the fix is to send the model a compact summary (top N fares, short ids) and keep the full offers in state.

19. Questions + answers

Why LangGraph and not a plain while-loop?

Three things I'd otherwise build myself: checkpointing per thread, interrupts that pause and resume, and explicit conditional routing that makes the safety rule visible in the graph. The loop itself is simple; pausing for a human across a server restart is not.

How do you stop the model from booking without permission?

Structurally: the router sends every book_flight call to the approval node, which calls interrupt(). The tool only runs after a human's Command(resume="approved"), the server checks the approval id, and the approval expires with the fare. The prompt also says "don't ask for confirmation yourself", but safety doesn't depend on the prompt.

What happens if the user double-clicks Approve?

The first click resolves it and starts the turn. The second one finds the same decision in session.resolved and returns 202 without running anything. If it were a different decision, it would get 409 approval_already_resolved.

What if the server crashes while waiting for approval?

The interrupt is in the Postgres checkpointer and the UI state is in chat_sessions. After a restart, the browser reconnects, gets the snapshot including the pending approval, and approving resumes the graph.

How do you handle webhooks arriving twice or out of order?

Twice: a unique (provider, event_id) constraint, and the duplicate is ignored. Out of order: the state machine, where PAID is terminal and an illegal move changes nothing. Both the webhook and /sync go through one function.

How do you validate LLM output?

Tool arguments go through Pydantic's model_validate_json. A failure becomes a tool error message that the model sees and corrects. Schemas come from the same Pydantic models, so the prompt and the validation can't drift apart.

Why SSE instead of WebSockets?

Traffic is one-way, server to client; actions are POSTs. SSE is plain HTTP, reconnects by itself, and has Last-Event-ID. I add a snapshot on connect so a reconnecting client is never out of sync.

How would you scale it to many servers?

The checkpointer and database already work across instances. What needs to move: the event bus to Redis pub/sub, the turn lock to Redis or a Postgres advisory lock, and the session projection read from the database. The MCP client would use a pooled long-lived session.

How do you know it works? How would you evaluate the agent?

Today: 62 integration tests with a scripted fake LLM check the routing, approvals, payments and restarts. Next: a trajectory eval set (expected tool order, no redundant calls, never book without approval), like the 40-question harness I built for my RAG project.

What does it cost per conversation?

I log input and output tokens per call. A finding: ~15k input tokens per call, because the flight offers stay in history. Summarising them is the biggest saving.

21. Self-quiz (answer out loud, then open)

Q1. Why does anything before interrupt() run twice?

On resume, LangGraph re-runs the whole node from the start; this time interrupt() returns the value instead of pausing.

Q2. Semaphore(3) vs RateLimiter(5): what does each limit?

The semaphore limits calls in flight at once; the rate limiter limits how many calls start per second.

Q3. Why is the Cashfree order id our UUID and not Duffel's id?

The webhook must find our booking directly, and our id is stable and under our control.

Q4. Why subscribe before taking the snapshot?

So an event published between the two steps is in the queue; anything already in the snapshot is skipped by id.

Q5. Why does a FAILED payment allow PAID?

The provider can report a late success; the money did move, so success wins.

Q6. Why return 404 for someone else's thread?

403 would confirm that the thread exists, which leaks information.

Q7. What breaks if you run two copies of the API?

The in-memory event bus and turn lock: a browser on server A won't see events from a turn running on server B.

Q8. Why do services commit and not repositories?

One business action is one transaction; if repositories committed, a booking could be half-saved.
